# LinguaSchool: етап 5. Розклад та індивідуальні уроки - детальний план

Oct 9, 2026 · @Alex Hamenko

Після етапу 5 (приблизно 3-4 тижні) викладач задає доступність, студент бронює урок через API, переносить або скасовує його за правилами школи, а система нагадує про уроки і створює відеокімнату. Баланс уроків - append-only ledger.

Попередній: [етап 4](stage-4.md). Модулі: `Teaching` (доступність) і `Scheduling` - перший модуль із шарами DDD (`Domain/Application/Infrastructure/UI`). Усе через API, UI кабінету - пізніше.

## Етап 5. Розклад та індивідуальні уроки (≈3-4 тижні)

### 5.1 Шари модуля Scheduling (≈1-2 дні)

1. Структура `src/Scheduling/{Domain,Application,Infrastructure,UI}`. `Domain` не залежить від Symfony і Doctrine-сервісів (атрибути маппінгу - свідомий компроміс або XML/PHP-маппінг в `Infrastructure`; вирішіть і зафіксуйте рішення в ADR-нотатці).
2. `deptrac.layers.yaml`: правила між шарами (`Domain` ні від кого, `Application` -> `Domain`, `Infrastructure` і `UI` -> `Application` + `Domain`). Другий виклик Deptrac у `make qa`.
3. Value objects: `LessonId`, `TimeSlot` (start + 50 хв, лише UTC), `StudentId`, `TeacherId`. Інваріанти - у конструкторах.
4. Репозиторій - інтерфейс у `Domain`, реалізація на Doctrine в `Infrastructure`.

**Що вивчаєте:** шари DDD, value objects, Doctrine embeddables і custom types, Deptrac для шарів.

### 5.2 Доступність викладача (≈3 дні)

| Сутність | Поля |
| --- | --- |
| `AvailabilityRule` | id, teacherId, weekday, startTime, endTime (локальний час викладача), validFrom, validTo |
| `AvailabilityException` | id, teacherId, startsAt, endsAt (UTC), reason (відпустка, лікарняний) |

1. Генератор слотів: правила в таймзоні викладача -> слоти UTC на період; мінус винятки, мінус уже заброньовані уроки, мінус буфер між уроками. Чиста доменна логіка, вхід - `ClockInterface` і дані.
2. Переходи на літній/зимовий час: урок о 10:00 за Києвом має лишатися о 10:00 після зміни часу. Тести на дати переходу обов'язкові.
3. API: `GET /api/teachers/{id}/slots?from=&to=` (у таймзоні студента з профілю), CRUD правил і винятків для викладача (`/api/teacher/availability`, voter: лише свої).

**Що вивчаєте:** таймзони і DST, `DateTimeImmutable`, `MockClock`, API Platform з кастомними providers.

### 5.3 Бронювання і ledger (≈4 дні)

| Сутність | Поля |
| --- | --- |
| `Lesson` | id, studentId, teacherId, startsAt (UTC), status, isTrial, videoRoomUrl, cancelledAt, cancelReason |
| `LessonBalanceEntry` | id, studentId, delta (+8, -1, +1, +3), reason (enum), reference (id уроку/замовлення), createdAt |

1. Баланс = сума записів ledger. Записи ніколи не змінюються і не видаляються; виправлення - новим записом. Подумайте, як рахувати баланс швидко (агрегат у запиті vs кешований знімок).
2. Команда `BookLesson` (Messenger command bus, sync-транспорт) і хендлер: перевірка балансу, вільного слота, ролі. Резервування уроку списує 1 урок при бронюванні чи при проведенні - вирішіть і зафіксуйте.
3. Подвійне бронювання: унікальний індекс `(teacher_id, starts_at)` у БД - остання лінія оборони; `LockFactory` з ключем на викладача - щоб не впиратися в помилку БД; транзакція навколо перевірки і запису. Розберіть, чому одного лише `if (slotIsFree)` недостатньо.
4. Пробний урок: бронюється з ліда (етап 3) без балансу, один на студента.
5. Поки білінгу немає, баланс поповнює адмін записом ledger в EasyAdmin (на етапі 6 - через оплату).

**Що вивчаєте:** command bus, `symfony/lock`, транзакції, унікальні індекси, append-only модель.

### 5.4 Workflow уроку (≈2 дні)

1. `state_machine` "lesson": `requested -> scheduled -> in_progress -> completed`, а також `cancelled_by_student`, `cancelled_by_teacher`, `no_show`.
2. Guards на переходах (хто і коли може перейти) і слухачі подій Workflow: `completed` -> запис у журнал, `cancelled_by_teacher` -> повернення уроку (+1), `no_show` студента -> урок згорає.
3. Доменні події `LessonScheduled`, `LessonCompleted`, `LessonCancelled` для інших модулів (`Notification`, пізніше `Learning`).
4. Відеокімната: при переході в `scheduled` генерується посилання Jitsi (`https://meet.jit.si/<випадкова-назва>`); генератор за інтерфейсом, щоб пізніше замінити провайдера.

**Що вивчаєте:** Workflow (guards, events, marking store), доменні події.

### 5.5 Перенесення і скасування (≈3 дні)

1. Правила: не пізніше ніж за 6 год до початку; 2 безкоштовні перенесення і 2 скасування на календарний місяць (у таймзоні студента - вирішіть і задокументуйте). Пізнє скасування - урок списується.
2. Доменна політика `ReschedulePolicy`/`CancellationPolicy` повертає рішення з причиною (а не `bool`), щоб API пояснював відмову.
3. Voter `LessonVoter` (`RESCHEDULE`, `CANCEL`) делегує політиці; дії API: `POST /api/lessons/{id}/reschedule`, `POST /api/lessons/{id}/cancel`.
4. Перенесення = атомарно звільнити старий слот і зайняти новий під тим самим lock.

**Що вивчаєте:** Voters з доменною логікою, `ClockInterface` у тестах, транзакційні сценарії.

### 5.6 Нагадування (≈2 дні)

1. `symfony/scheduler`: `RecurringMessage` кожні 5 хв шукає уроки, що починаються через 24 год і 1 год. Окремий процес `messenger:consume scheduler_default` (додайте до compose-сервісу `worker`).
2. Ідемпотентність: позначка "нагадування X відправлено" на уроці або окрема таблиця, щоб повторний запуск не дублював листи.
3. Канали: email і Telegram (якщо користувач підключив), час у листі - у таймзоні отримувача.

**Що вивчаєте:** Scheduler, idempotent-хендлери, локалізація дат (`format_datetime` з таймзоною).

### 5.7 Тести й готовність етапу 5 (≈3 дні, паралельно з рештою)

1. **Unit:** генератор слотів (включно з DST), політики перенесення/скасування на межах (6 год рівно, 3-тє перенесення в місяці), розрахунок балансу.
2. **Integration:** унікальний індекс відкидає дубль, lock не дає двом бронюванням пройти одночасно (два процеси або два з'єднання), Workflow-переходи змінюють ledger.
3. **Functional (API):** повний сценарій студента: слоти -> бронювання -> перенесення -> скасування; викладача: розклад, `completed`, `no_show`; чужий урок - 403.
4. **Scheduler:** запуск задачі з `MockClock` створює рівно одне нагадування.

**Готовність етапу 5**

- [ ] Викладач керує доступністю, студент бачить слоти у своїй таймзоні
- [ ] Бронювання не допускає подвійних записів навіть під конкурентним навантаженням
- [ ] Workflow уроку зі всіма станами, ledger змінюється лише новими записами
- [ ] Правило "6 год, 2 на місяць" через voter і доменну політику
- [ ] Нагадування за 24 год і 1 год, без дублів
- [ ] Посилання на Jitsi у запланованому уроці
- [ ] Deptrac (модулі й шари) без порушень, `make qa` і `make test` зелені
